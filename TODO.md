- [ ] Self-updating satellite deployment (TUF?) — today a satellite is either a manually-started laptop process (stop it when you leave, per "Running modes" in `designs/satellites.md`) or, eventually, permanent kit at each house with no update story at all once it's set up (provisioning itself is also still an open question there). The central server has this solved twice over: Watchtower polls GHCR and swaps container images, `capture-sync` (a systemd timer) separately pulls `main` and reconciles `docker-compose.yml` for changes Watchtower can't see. A permanent satellite needs its own version of one of these. Worth weighing:
  - **TUF** (The Update Framework) — real protection against a compromised/stale update source (rollback, mix-and-match, endless-data attacks), via layered signed metadata (root/targets/snapshot/timestamp roles). Standard choice for fleets of unattended devices open to a hostile network (IoT, package registries). Meaningfully heavier than anything else in this stack — key management/rotation, a repository to host signed metadata, a client (`python-tuf`/`go-tuf`) on the satellite.
  - **Simpler git-pull + restart**, mirroring `capture-sync` exactly — a systemd timer pulls `main`, rebuilds the frontend if it changed, restarts the satellite process. Much less to build and reason about; the honest question is whether TUF's threat model (a hostile update source) is real here given the whole point of this system is Tailscale-only, single-user, no public exposure — the same reasoning that's already justified skipping TLS between internal services (see Hub → satellite dispatch in the design doc).
  - Either way, this only matters once permanent kit exists — a laptop-bootstrapped satellite is inherently attended (you're the one starting/stopping it), so has no real gap here yet.

## ideas (freeform)

Unstructured thoughts on where this could go, captured as-is — not scoped or committed to.

- **Physical/kiosk input**: a push-to-talk interface, physical or touchscreen, with the UI running in kiosk mode on a Raspberry Pi.
- **Child and parent modes** — some actions should require parent mode to invoke.
- **Auditing** — actions taken by the app should be logged/auditable. Partial start: `plan_progress` (see `TOL-5` below) persists which read-only steps a plan actually ran, though not yet the acting-step execution itself.
- **Home automation control**: Spotify, Sonos, a Matter hub (IKEA Dirigera).
  - [x] Dirigera light control implemented and verified against real hardware (`designs/matter-lighting.md`): `resolve_light` (readonly — matches free-text room against Dirigera's own rooms, validates action/brightness) followed by `control_light` (acting — proposes the exact resolved room; on/off/dim), the same two-step resolve-then-commit shape `resolve_playback`/`control_playback` established for Sonos. `satellite/services/dirigera.js` talks to a real hub via the `dirigera` npm client. Two bugs found and fixed once real hardware was in the loop: brightness validation rejected numeral strings (`Number.isFinite` doesn't coerce, and `propose_plan`'s untyped `args` field doesn't guarantee Claude emits a JSON number); and the favourites sidebar's form-edit override was silently dropped by a wiring bug in `main.js` (`onRun: (id) => handleFavouriteRun(id)` discarded the collected overrides), so editing a favourite's brightness via its form replayed the original frozen value instead.
  - [ ] Query-style captures ("what's the temperature in the living room in Tollington?") — answered mostly by machinery that already exists: a `readonly` step reads the value, a `terminal` step's `action_result` interpolates it via `${stepId.field}` (same pattern `search_linear_issues` and now `resolve_light`/`resolve_playback` already use). One real gap: a pure answer doesn't cleanly fit any existing terminal status (not `triaged` — nothing to review later; not `acted` — nothing was done) or the resolve-in-place-after-1.5s UX, which may not be the right interaction for "ask and get an answer." Pin — revisit if a second real need for it shows up.
- **Push to external services**: tasks and calendar items into things like Proton Calendar, Linear, possibly Obsidian.
- **Drive custom-built apps too**, not just third-party services — these would need to be reachable on the same Tailscale network.
- **A third form factor: "remote"** — a native Android app, on the phone, that's *not* a satellite (no fixed location, no local device discovery of its own) but still wants the satellite UI's "an action brings up a little local control" behavior (see the local now-playing panel in `designs/satellites.md`'s Satellite-served frontend & local device controls). The trick that panel uses — a relative `/api/status` fetch that happens to reach the satellite because the satellite is the one serving the page — doesn't apply to an installed app with no fixed origin. It'd instead need to resolve which satellite to talk to itself (`GET /api/satellites` already returns each house's `address`) and then hit that satellite's `/api/status`/`/api/pause`/`/api/volume` directly, same protocol as the local panel today, just orchestrated by the app instead of served from the satellite — needs the phone on the tailnet, same as everything else here. Otherwise talks to the central backend the same way the general frontend does (capture, inbox). Just a thought, not scoped.
- [x] **Favourites**: named shortcuts (e.g. "play [song]") that just replay a fixed, previously-approved sequence of tool calls when invoked — no new planning/approval step needed each time. Implemented: since a plan always terminates at exactly one `acting` step with fully-resolved args (see `processCapture()` in `claude.js`), "the little program" a favourite freezes is just that one `{ tool, input }` call — captured as `executed_action` on the item when `POST /api/items/:id/approve` runs it (a new column, kept permanently, unlike `pending_action` which is cleared). `POST /api/items/:id/favourite` (only valid on an `acted` item with an `executed_action`) copies it into a `favourites` row under a label (the item's `action_result`, e.g. `Played "Silver Machine" by Hawkwind on Bedroom`). `POST /api/favourites/:id/run` replays it via `executeAction()` directly — no LLM call, no re-resolution, no approval gate — and records the replay as its own new item (resolved straight to `acted`/`failed`) so it shows up in the inbox like any other capture, for an audit trail. Frontend: a ☆ button appears on the result strip of any favouritable item (turns to a disabled ★ once favourited); a sidebar (`favourites.js`) lists saved favourites with their description/label, a one-click "run again," and delete — sits beside the inbox on a wide viewport, stacks above it on mobile (this app is phone-first).
  - **Frozen by default, but replayable with edits**: replaying `control_playback` still defaults to the exact `speaker`/`track` object resolved at original approval time, not a fresh `resolve_playback` lookup — matching how the rest of the acting-tool design treats "what got approved" as the literal thing that should happen (see `designs/satellites.md`'s Safety section). A subtlety worth knowing: if a Sonos room gets renamed, or a `target_house` config changes, an unedited favourite can start failing even though a fresh capture with the same text would still resolve fine. See the "favourite as a form" entry below for the escape hatch.
  - Replay **skips approval entirely** — the one deliberate departure from this app's "never fire blind" rule, justified because a human already approved this exact resolved action once, at favourite time. No dedup either: replaying `create_linear_task` creates a new Linear issue every time by design (that's what makes it a useful shortcut for e.g. a recurring task), so it's a poor fit for anything where a duplicate side effect would be unwelcome — favouriting is an intentional per-item choice, not something to do automatically.
  - [x] **Favourite as a form, not just a frozen call**: a favourite (and a still-`awaiting_approval` proposal) now remembers `plan_steps` — the literal program (readonly + acting steps, with their original, unresolved args) that produced it, not just the one frozen `{ tool, input }` call. `getFormFields()` in `claude.js` walks a program's readonly/acting steps and pulls out their literal (non-`${ref}`) arguments as an editable form — e.g. `resolve_playback`'s `title`/`artist`/`room`, or `create_linear_task`'s `title`/`description` directly. The frontend renders these as inputs: on an `awaiting_approval` item, above the approve/veto buttons; on a favourite, inline once "run again" is clicked. Submitting either sends `{ overrides: { stepId: { field: value } } }`, and `runProgram()` (the interpreter loop factored out of `processCapture()`) re-runs the saved steps with those fields substituted in — so editing `resolve_playback`'s room really does re-search for a speaker, it doesn't just patch display text. `POST /api/items/:id/approve` and `POST /api/favourites/:id/run` both accept this optional `overrides` body; omitting it keeps the old exact-replay/approve-as-proposed behaviour verbatim. A recompute that no longer resolves to an acting step (e.g. an edit that empties a required field) 422s before anything executes, rather than firing on bad input.
- **Proposed flow**: typed or voice input is processed by the LLM into a plan — a schedule of tool calls plus target location/device — along with prose repeating back what was asked. The prose and a description of the plan are played back to the human, who approves or vetoes before anything executes.
  - [x] Implemented for single-tool-call captures: `create_linear_task` now proposes (`awaiting_approval`) rather than executing immediately; `POST /api/items/:id/approve`/`/veto` decide. Any future acting tool gets this by being added to `ACTING_TOOLS` in `backend/integrations/claude.js`.
  - [x] `TOL-5` — multi-step plans: `processCapture()` now asks Claude for one `propose_plan` call (an ordered list of steps) instead of forcing a single tool per capture. Steps are `terminal`/`acting` (end the plan) or `local`/`readonly` (run automatically, output bound for later steps via `${stepId.field}` refs) — one round trip to Claude, then a deterministic interpreter runs the rest. First use case: `search_linear_issues` (read-only) lets a plan check for an existing similar issue before branching to `create_linear_task`, so captures don't create duplicate Linear work. Calendar integration (Google/CalDAV) would be the next real exercise of this — still not implemented (see above).
  - [x] Readonly plan steps are now visible as they run: `processCapture()`'s `onStep` callback persists a growing `plan_progress` list (per-tool `label` in `TOOL_REGISTRY`) that the frontend renders as a checklist above the shimmer/result, and it stays visible afterward as a small trace of what the plan actually checked. `pollForResolution` resets its backoff whenever `plan_progress` grows, so it keeps polling briskly while a plan is actively making progress rather than backing off on a fixed schedule.
- **Integrations tab in the UI** — a tab showing which integrations are currently enabled (e.g. Linear on/off based on whether it's configured).
  - [x] Minimal version implemented (`TOL-6`): enabled integrations shown in the version footer, not a dedicated tab. A fuller tab (with per-integration detail/config links) is still open if wanted later.
